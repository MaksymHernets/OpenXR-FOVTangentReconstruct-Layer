Ordinary Vulkan applications remain in diagnostic passthrough. No automatic Vulkan function interception is installed by this OpenXR layer. The experimental developer cooperation API is an explicit contract, not a heuristic or a claim of third-party compatibility.

## Required relationships

1. **Application rendering completion.** Before releasing each input image, a cooperating application supplies its acquired image index, exact attachment layout, session-bound VkQueue, and a producer VkFence. That fence must cover all rendering and ownership restoration of that image on the bound queue. The layer checks `vkGetFenceStatus == VK_SUCCESS` at release without waiting. An absent, stale, wrong-index, wrong-queue, unsupported-layout or incomplete declaration prevents source capture. A fence alone does not reveal a layout: the exact layout is a separate caller obligation.
2. **Ownership and layout.** Input images must be owned by the session's bound queue family and must use exactly COLOR_ATTACHMENT_OPTIMAL or DEPTH_STENCIL_ATTACHMENT_OPTIMAL, as appropriate. The declaration is consumed once per successful acquire/wait/release generation. The layer copies to its own sampled image using ALL_COMMANDS/MEMORY_WRITE -> TRANSFER/TRANSFER_READ barriers, then restores the declared layout before forwarding release. No other application thread or queue may access the image concurrently or submit more writes after the declared fence. These are mandatory developer API obligations, not observations inferred by the layer.
3. **Reconstruction submission.** All optimizer commands use the application's session device and bound queue. Vulkan 1.1 pipeline barriers cover private-image producer/consumer hazards. Each command slot owns a command buffer, fence, uniform buffer and descriptors; a slot is reused only after its fence completes. No queue submit/submit2, render-pass, dynamic-rendering, semaphore or barrier function is globally replaced. Timeline semaphores and synchronization2 are not required or enabled after device creation.
4. **Reconstruction completion.** Optimizer submissions end with explicit transfer/storage-write -> MEMORY_READ barriers and restore output images to COLOR_ATTACHMENT_OPTIMAL. Their GPU work is ordered before later operations on the same bound queue. OpenXR's externally synchronized queue-access contract covers release and end-frame: the cooperating caller must hold its queue lock around these calls, and cannot race them with Vulkan queue submissions. The runtime's subsequent queue consumers must honor the OpenXR Vulkan synchronization contract. This is a GPU dependency chain, not a claim that xrReleaseSwapchainImage is a CPU fence.
5. **Release and runtime consumption.** Source capture is submitted before forwarding input release; only private captured images are read at end-frame. Output images are acquired and successfully waited, then written and restored before their release. The first write to each output array layer may discard previous contents using UNDEFINED, because the referenced destination region is fully overwritten. Subsequent packed-eye writes preserve prior content using tracked COLOR_ATTACHMENT_OPTIMAL. The layer never reads old output content. Only fully submitted reconstructions replace copied projection views; application structures are untouched.

## Failure and lifetime rules

- Passthrough before cooperation leaves application FOV, recommendations, images, and extension chains untouched. A failed capture/reconstruction after a cooperative FOV request retains the application's submitted image/FOV pair; it must not attach a widened FOV to an unprocessed image.
- Format/usage/sample-count checks precede Vulkan image access. No storage usage is inferred from a VkImage handle. Output uses direct storage only when requested/accepted and supported; otherwise it uses a private RGBA8 compute target and a legal transfer-destination runtime image.
- A nonblocking ring-capacity failure selects fallback; ordinary frame processing performs no `vkQueueWaitIdle`, `vkDeviceWaitIdle`, or fence wait.
- Source/history/scratch images and image views are owned by the optimizer. Runtime VkImages, VkDevice, VkQueue, VkInstance and VkPhysicalDevice are borrowed and never destroyed by it.
- Destruction/resize/history eviction drain only optimizer submission fences before freeing referenced resources. Teardown may block for outstanding optimizer work. Device loss is reported; the optimizer does not attempt to recreate the application's device.
- The API cannot validate a lying caller's fence provenance or command-buffer contents. Only developer-owned applications explicitly satisfying this contract may opt in. Unsupported third-party applications must not be enabled by setting an environment variable or merely selecting an algorithm.

## Normative basis and limits

The [OpenXR Vulkan concurrency/state requirements](https://github.com/KhronosGroup/OpenXR-Docs/blob/main/specification/sources/chapters/extensions/khr/khr_vulkan_enable.adoc) require bound-queue ownership and external synchronization of acquire, release, begin-frame and end-frame. Vulkan [pipeline barriers](https://docs.vulkan.org/spec/latest/chapters/synchronization.html) establish the actual execution and memory dependencies on that queue. Same-queue submission order alone is insufficient; the barriers are required.

General third-party processing requires an additional integration that establishes these facts for arbitrary application queues and layouts, such as a separately negotiated Vulkan layer. It is not implemented or advertised by 0.1.4. Controlled fixture evidence does not establish SteamVR or VDXR compatibility.

## Executed validation

All nine Vulkan GPU/dispatch cases ran with source-built Khronos validation v1.3.290 and `VK_VALIDATION_FEATURE_ENABLE_SYNCHRONIZATION_VALIDATION_EXT`, with zero reported validation errors including teardown. The fixture fails when validation is required but unavailable. See [execution evidence](vulkan-evidence/validation-execution.txt). This checks the controlled queue/layout contract; it does not prove an unknown application's fence provenance or arbitrary cross-queue behavior.
