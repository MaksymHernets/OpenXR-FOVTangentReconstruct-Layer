# Experimental D3D12 FFR cooperation API

`layer/FFRCooperation.h` declares versioned layer-specific functions obtained through the layer's `xrGetInstanceProcAddr`. They are not a registered OpenXR extension. This integration is for developer-owned applications; it does not install Vulkan interception, replace COM vtables, modify games, or bypass integrity checks.

1. Enable FFR in the selected profile. Use a D3D12 session on a single-node Tier 2 device and a DIRECT session queue. Unsupported configurations must keep normal rendering.
2. Locate stereo views. The exact latest locate display time identifies the layer's authoritative per-eye plan. Scene scopes cannot use a stale/unknown frame, invalid tracking, or a frame already ended.
3. Acquire and wait for a supported single-sample color swapchain. Supply the actual per-eye subimage/viewport. Array and packed/separate targets require a **separate scene scope per eye**; single-pass stereo with one shared map is not supported. The caller is responsible for binding the matching render target, array slice, viewport and compatible scene pipeline.
4. Before recording scene draws, outside D3D12 render passes, call `xrFovBeginD3D12FFR(session, &drawInfo)`. Provide the open DIRECT command list, a free slot (0–7), and a dedicated same-device fence/future completion value. This is explicit acceptance of the contract. The initial list state must be 1x1 shading with no rate image. Pipelines must support the selected single-sample VRS rates; sample-frequency/depth-writing shader restrictions remain the caller's responsibility.
5. Record scene draws. The layer uses the supplied subimage rectangle and the saved projection; it does not modify viewports or FOV here. End with `xrFovEndD3D12FFR(session, commands)`, restoring 1x1 and a null rate image with passthrough combiners. End each scope before another eye, image release, reconstruction, or end-frame. Nested scopes and premature session destruction are refused.
6. Execute the list on the session-bound queue, externally synchronized by the application. Signal the dedicated fence **on that queue after execution**. Do not CPU-signal it, reset it, signal it from another queue, discard the recorded list, or reuse the promised value for new work. Different slots in the same submission may share a value; subsequent submissions must increase it. Do not race command recording with slot reuse.
7. Release the source image and submit the existing projection normally. The established Reconstruction Manager handles any actual crop. There is no second crop or third rendered zone outside the active projection.
8. Keep the session/device/fence/resources alive until completion. Reusing a busy map fails without waiting. Session destruction is refused until all scene scopes end and promised GPU work completes. No normal-path queue/device idle or GPU fence wait is inserted by FFR. Invalid callers lacking completion proof cannot safely free referenced resources; the backend retains such references until process teardown.

The layer validates device identity, DIRECT list type, future fence value, slot availability, current projection provenance, swapchain/session membership, acquisition/wait, single sampling, format and subimage bounds. It cannot inspect an application's complete draw/PSO history, prove a lying fence's provenance, or observe arbitrary application queues. These are reasons to require cooperation, not to assume general game compatibility.

The API does not preserve arbitrary preexisting application VRS state because D3D12 does not expose a getter for it. Its explicit initial-state contract allows End to restore the known baseline. A post-End raster draw is checked with pipeline statistics at an area that would otherwise be coarsely shaded, proving restoration in the fixture.

See [Microsoft's shading-rate image requirements](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist5-rssetshadingrateimage) for image/combiner rules. For Vulkan, [Khronos's shading-rate integration](https://docs.vulkan.org/features/latest/features/proposals/VK_KHR_fragment_shading_rate.html) requires enabled device features and attachment/pipeline integration absent from this OpenXR-only backend. [NVAPI](https://docs.nvidia.com/nvapi/group__dx.html) offers vendor-specific D3D11 interfaces, but no verified D3D11 scene integration is installed here.
